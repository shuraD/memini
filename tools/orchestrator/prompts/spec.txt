   Rules for the spec:
   - One small slice: about 150 lines of code or less, one or two hours. If the task is bigger,
     write the first coherent part and say in the out_of_scope list what is left.
   - paths lie inside $module and inside the allowed code paths (rules below).
   - Generic code only: no business names, no provider or customer names in the interface.
   - Everything a test checks must be stated in interface or acceptance.
   - Every card line the task text names (an id like A14) needs two lines in the acceptance
     list: `- A14: Given ..., Then ...` (the criteria) and `- A14 done: <the observable end
     state that means the card line is finished>`. Name the id in a test name or a comment of
     the hidden test that proves each. A spec or test set missing any of these is refused.
   - A task text with no card line has an `Acceptance:` part and a `Done:` part. Write one
     acceptance line per item of the `Acceptance:` part (items are separated by `;`), numbered
     in order: `- AC1: Given ..., Then ...`, `- AC2: ...`; add one line `- done: <the
     observable end state of the `Done:` part>`. Name each id (AC1, AC2, ...) in a test name or
     a comment of the hidden test that proves it. A spec or test set missing any is refused.

2. Write the hidden tests: NEW files named test_*.py (where: see the rules below).
   - They test the observable behaviour of the spec, not an implementation you imagine.
     Each test states its expectation with an assert.
   - They must fail now (the code does not exist yet) and pass once the spec is implemented.
   - Deterministic: no network, no clock, no randomness without a fixed seed, no skips.
   - Never replace or reassign interpreter-wide state (os.environ, sys.modules, builtins,
     sys.stdout): pytest itself uses it. To prove code does not read something, record the
     calls with monkeypatch only around the call under test.
   - Do not change any existing file. Do not write any implementation code.
   - Contract first: from a task you depend on, use only its contract (types, protocols,
     errors, fakes named in its spec). Where its behaviour is needed, use the contract's
     fake or a fake defined in your test, so this slice can be built and tested alone.
   - Never write a value that looks like a real secret (API key, token, password), even in a
     test: use an obvious fake such as "test-key". A secret scan rejects anything else.
