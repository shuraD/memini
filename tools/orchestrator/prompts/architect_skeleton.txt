How to work
- Generic minimal MVP. The old feature as the old code did it, nothing more. Libraries first. Few files per directory. Fewer, deeper functions: group the card lines the old code served in one function into one function.
- The code already on main stays: every existing public function is a row with its exact signature.
- Every function is on the path of at least one top caller. A top caller is where a flow starts: a command, a tool of a server, a public call.
- Every claim carries its evidence: a card id, an old-code file and line, a file and line of an installed package, or a read-only query you ran. What you could not check is listed as not verified, never stated as fact.

One functionality, every interface
- Every interface that offers a functionality calls the SAME function. An interface never gets its own second implementation; the difference between interfaces is only the interface.
- Give every functionality a stable id. Write the id in the Note of the function that implements it and in the Note of every interface row that calls it. List the functionalities in one table: id, what it is for in one plain sentence, the one function that implements it, the interfaces that expose it. A later unit that adds an interface then only calls a function that already exists.
- For every entry point, say in one sentence what it was used for in the old code.

Reuse
- Before a new row, look for an existing row that does the same work: use it, or extend it and use it. Go over the whole document once more at the end and merge rows that implement the same logic under two names.

Flows
- Write the path of each top caller down to the stored data, step by step. Describe a flow by the kinds of input it handles and how each kind is routed, as the old code did it.
- Show every capability a reader will look for in the flows that trigger it, also the ones that run as a side effect of a write.
- Mark every function whose old implementation is a regular expression, and say whether the old code already had another path for it. Prefer a library or an existing prompt path to a new regular expression; add a regular expression only when nothing else does the job.

Feature flags
- List each feature flag: what it switches and which functions read it. A row whose behaviour depends on a flag says so in its Note.

Questions
- Before a question goes to a person, read the old code: find why it was built that way (the caller, a comment, a document) and answer the question yourself when the old code settles it.
- What the old code cannot settle is a decision for the owner: the question in one sentence, what the old code did and why, your recommendation. Where a wish differs from what the old code did, never change the scope silently: list it as a decision.

The skeleton document: $doc_skeleton
- The machine reads every table with exactly this header, one row per function; prose and other tables go around them:
| Id | File | Function | Signature | Cards | Top caller | Used by | Note |
- Id: a short unique id of the row, one token. File: the path of the source file. Function: the qualified name (Class.method for a method). Signature: the exact def line, a | inside it written \|. Cards: the card ids the function serves, - for none. Top caller: <dotted.module>:<function> of every flow the function is on; a row that names itself is a top caller. Used by: the ids of the rows that call it, - for a top caller that nothing calls. Note: the functionality id, the flag, the reason a row without a card exists.
- A row of code already on main whose signature an owner-approved fix changes carries the marker APPROVED-FIX and the fix's id in its Note. No other existing row may differ from the code.
- Size budget: one table with a row per file: the one-line reason the file exists (a layer boundary, a different owner, an entry point; "it would be long" is no reason below the file limit), its function rows, its lines on main today, its estimated lines, and where that stands against the KPI. Then the totals against every measure of the KPI. Where a limit is passed, say what you merged or cut, or list it as a decision.
- Also in this document: the functionalities table, the entry points table, the flows, the feature flags, the decisions for the owner.

The schema usage proof: $doc_schema
- The rule: every stored item has a writer and a reader. An item that is written and never read is fixed one of two ways: the reading functionality is added, or the item is removed.
- One row for every item the data schema declares (every kind of record, every kind of link between records, every field), and one row for every item the skeleton proposes to add: the item, the skeleton row that writes it and the row that reads it (by row id), the entry points that need it, where the old code used it (file and line), and a verdict.
- Verdicts: KEEP (it has a writer and a reader), ADD-READER (it had none; name the row that now reads it, and say so in that row's Note in the skeleton), REMOVE (nothing used it; say what you checked), ADD (not declared today and a card of the scope needs it; name the card).
- A summary with the count per verdict, and a list of old data you considered and did not add because no flow of the scope reads it.

The library usage review: $doc_libraries
- For every function of the skeleton, merged or planned, that does work a data store or a package commonly provides (storing, searching, model calls, batching, retries, splitting, schema set-up): what it does, what the data store and the installed packages already provide for it (the file and line, or the built-in, where you saw it), a verdict, and the lines saved. Verdicts: USE THE LIBRARY, ALREADY USES IT, KEEP.
- A summary with the counts per verdict, merged and planned apart, and the packages checked with their installed version and licence.
- The fix list for merged code: each fix with its id, what is wrong today, the exact change, the signatures it changes (these rows carry APPROVED-FIX in the skeleton once the owner approves the fix), and how to prove it.
- A "Not for production" list: whatever you found that is experimental, deprecated, not installed, or was never run.
- What could not be verified, and the open points that need a decision.

The reuse review: $doc_reuse
- Read every function row of the skeleton again as a reviewer who did not write it. Find functions that do the same work, and functions that differ only by data (one function plus config would do).
- One finding each, ranked by lines saved: the rows involved (by id), why they are the same work, the old-code evidence, the single function you propose (its row id and signature), the estimated lines saved, and SURE or CHECK.
- A summary: the function rows read, the findings, the lines saved, the total against the KPI. Apply every SURE finding to the skeleton before you finish and say so; list what you looked at and did not propose.
